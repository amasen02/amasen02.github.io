Draft post · REST APIs

An idempotency key is more than a header—it is a replay contract.

  1. Atomically claim or read the key so concurrent duplicates cannot execute the handler twice.
  2. Bind the key to the user, method, path, and request-body hash to prevent mismatched requests from sharing state.
  3. On a matching retry, replay the original response instead of running the handler again.
  4. Release keys after transient 5xx or infrastructure failures; retain deterministic 4xx outcomes for replay.
  5. Recover crashed in-progress requests by taking over expired locks and rerunning the handler.

Design your retry path around the failure cases, not just the happy path.

Source notes for the caption

Why the key and body must agree

The HTTPAPI working group draft defines a request fingerprint as a payload-derived way to establish request uniqueness. It describes replaying a completed operation and treating a concurrent duplicate as a conflict.

Stripe documents the concrete service behavior: later requests with the same key return the first result, while changed parameters produce an error.

  • IETF HTTPAPI draft 07 ↗Sections 2.2–2.7 · Internet-Draft
  • Stripe API reference ↗Idempotent request behavior

The IETF document is an expired Internet-Draft, not a published RFC. Status codes and retention policy remain part of each API’s documented contract.
