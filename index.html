freshcart-backend

Twelve .NET 10 microservices, each in a different architecture, with race conditions proven by tests

199 starsC#

A .NET 10 / Aspire reference e-commerce backend of twelve bounded contexts behind a YARP gateway, each context deliberately built in a different architectural style (Clean, Vertical Slice + Carter/MediatR, Hexagonal, 3-tier + Dapper, event-sourced, pipes-and-filters, CQRS read model) over a different store (SQL Server, PostgreSQL/Marten, MySQL, MongoDB, Redis, SQLite). Services talk asynchronously over MassTransit/RabbitMQ with transactional outboxes and synchronously over gRPC; a MassTransit state machine orchestrates the checkout saga across stock reservation, payment capture and confirmation. The gateway is a BFF: browsers hold an HttpOnly SameSite=Strict cookie, services only ever see a short-lived minted JWT. The Angular storefront lives in a separate repo (amasen02/freshcart-web); this one is the backend, plus Bicep IaC, Helm charts and per-service CI.

How it is built

src/ is one solution with four groups: BuildingBlocks (CQRS abstractions, MediatR behaviors, RFC 7807 exception handler, outbox + integration-event contracts, ServiceDefaults, security middleware), Services/ (twelve contexts, most split Api/Application/Domain/Infrastructure, some deliberately flatter — Inventory and Notification are single-project, Pricing is gRPC-only), ApiGateways/FreshCart.Gateway.Yarp, and AspireAppHost. Async integration flows through MassTransit over RabbitMQ; each writer stages events in its own store's outbox (EF Core on SQL Server, Marten on Postgres, Mongo transactions in Delivery/Payment) and a background OutboxPublisher drains them. Consumers are idempotent via a

What is interesting about it

  • Outbox drain is a claim-by-update with a crash-recovering lease, not a naive SELECT-unpublished. EntityFrameworkOutboxStore selects candidate ids, stamps them with a per-call ClaimId via a conditional ExecuteUpdateAsync that only matches rows still unclaimed or whose lease lapsed, then re-reads only the rows it actually won. Two publisher replicas therefore claim disjoint sets with no distributed lock, and a crashed drainer's rows return to the pool when the lease expires. The same pattern is implemented over Marten for the Postgres-backed Basket.
  • The payment one-payment-per-order invariant lives in the event store, not the read model. MongoPaymentEventStore builds a PARTIAL unique index on OrderId filtered to Version == 1 (the initiating event), so a second concurrent initiate for the same order fails with a duplicate-key error at the source of truth rather than in an asynchronously-projected SQL table. A compound unique (PaymentId, Version) index supplies optimistic concurrency, and the event batch plus a projection marker are inserted in one Mongo session transaction, so there is no dual write between the event store and the SQL read model.
  • Exactly-once read projections: WarehouseProjectionWriter writes the projection_inbox idempotency row inside the SAME MySQL transaction as the denormalised fact upserts, so an at-least-once redelivery cannot double-count additive aggregates (refund totals, customer lifetime value). Customer 'new vs returning' segmentation is decided from the prior lifetime-value row read inside that same transaction before the upsert advances it.

fastdl

Multi-connection segmented HTTP downloader CLI in .NET 10, with mirror striping and chunk resume

27 starsC#

`fdl` splits a file into fixed-size byte-range chunks and pulls them from a shared ConcurrentQueue with N parallel workers, writing each chunk straight to its offset in a preallocated file via RandomAccess.WriteAsync, so there is no shared file pointer and no lock. It handles single files, multi-file batches from a links file, recursive Apache/nginx autoindex folder mirrors with extension filtering, and multi-source striping where the same file is pulled across several mirror URLs. Interrupted downloads resume from a `.fdlmeta` sidecar holding a chunk bitmap, and post-processing can auto-extract downloaded zips (detected by PK magic bytes, not filename) or pack all outputs into one archive. When a server does not honour byte ranges, it falls back to a single-stream path that still handles resume, servers that silently ignore a Range header, and truncated bodies.

How it is built

Single executable project `src/FastDL` (AssemblyName `fdl`) with one class per concern and no DI container: Program.cs (parse -> build DownloadSpec list -> BatchDownloader -> post-process -> summarize), CommandLine.cs (hand-rolled argv switch, clamped values), HttpClientProvider.cs (one tuned SocketsHttpHandler shared by every worker), SegmentedDownloader.cs (the engine: probe, chunk-queue parallel path, single-stream fallback, per-segment retry with exponential backoff capped at 8s), BatchDownloader.cs (SemaphoreSlim-capped file-level concurrency), IndexCrawler.cs (depth-limited, root-confined autoindex crawler), ResumeStore.cs (sidecar chunk bitmap), ProgressReporter.cs (Interlocked counte

What is interesting about it

  • Chunk-queue work distribution instead of a fixed N-way split: workers dequeue from a shared ConcurrentQueue<int>, so a fast connection naturally claims more chunks and no single slow segment holds up the finish. Worker count is min(connections, pending chunks), so small files do not spawn idle tasks.
  • Mirror failover is folded into the retry loop rather than bolted on: the source for each attempt is `sources[(index + workerId + attempt) % sources.Count]`, so a retry deliberately lands on a different mirror instead of hammering the one that just failed, and normal (non-retry) traffic is already striped across mirrors by chunk index.
  • Two correctness guards against silent range corruption that most hobby downloaders miss. The probe sends a `Range: 0-0` request and accepts segmentation only if the reply is 206 with Content-Range exactly `{HasRange: true, From: 0, To: 0}` — a server that returns 206 while ignoring the Range would otherwise produce a file that is corrupt but 'successful'. Separately, AutomaticDecompression is set to None and `Accept-Encoding: identity` is sent, with the comment that auto-decompression corrupts byte-range math.

Verified in the repository

  • Real test suite: `tests/FastDL.Tests` with 6 xUnit files (SegmentedDownloaderTests, CommandLineTests, IndexCrawlerTests, ResumeStoreTests, ZipServiceTests, FormatTests) plus a Support/TestHttp.cs harness.
  • The test harness is a genuine fake: `RangeHttpHandler` implements real HTTP Range semantics (206 + Content-Range, or 200 when ranges are disabled) over an in-memory payload, so the segmented engine is tested deterministically with no network.
  • Segmented and single-stream output are asserted byte-identical by SHA-256 against the source payload — a real proof that the lock-free parallel offset assembly is correct, not just that it did not crash.
  • The resume test asserts `handler.SegmentRequests == 3` for a 4-chunk file with chunk 0 pre-marked, i.e. it verifies the absence of redundant refetching, not only the presence of a correct result.

dupesweep

Duplicate-file CLI: size → 64KB-hash → full-SHA256 funnel with reversible quarantine and restore

92 starsC#

`dsweep` walks one or more directory roots and reports groups of byte-identical files, ordered by reclaimable bytes. Detection is a three-stage funnel implemented in DuplicateFinder.cs: group by file length, then a SHA-256 of the first 64 KB, then a full-file SHA-256 on only the survivors, with stages 2 and 3 run through Parallel.ForEachAsync at a configurable degree of parallelism. Output is either a text report or JSON. Acting on the results is opt-in: `--apply quarantine` moves duplicates into a quarantine folder and writes a manifest.json of original→quarantine paths so `dsweep restore` can undo the whole operation, while `--apply delete` is the permanent alternative. Which copy survives is chosen by `--keep first|oldest|newest|shortest-path`.

How it is built

Single console project (src/DupeSweep, assembly `dsweep`) of 13 small single-responsibility files plus a parallel xUnit test project. Program.cs is pure orchestration (parse → scan → find → report → apply); every stage is a separate static class or small sealed type with no shared mutable state: CommandLine (hand-rolled argv parser, no dependency on System.CommandLine), FileScanner (manual recursive walk), Hashing (two-tier), DuplicateFinder (the funnel, the only stateful class, taking ScanOptions via a primary constructor), KeepSelector, QuarantineService, RestoreService, ReportWriter. Domain types in Models.cs are all sealed records (FileEntry, DuplicateGroup, DuplicateResolution, Manifest

What is interesting about it

  • The parallel hash pass writes results into a pre-allocated `string?[]` indexed by position rather than into a ConcurrentDictionary, then groups single-threaded afterwards. Interesting because it is lock-free on the hot path *and* it preserves scan order, which is what makes `--keep first` deterministic — a concurrent-dictionary implementation would have given order-dependent results for the default keep strategy.
  • Destructive work is reversible by default and the reversal is tested for the dangerous case. Quarantine is a File.Move plus a JSON manifest; RestoreService refuses to move a file back if something already exists at the original path, and the test `Restore_ExistingDestination_IsSkippedWithoutOverwrite` asserts both that the recreated file is untouched *and* that the quarantined copy still exists — i.e. it pins down that the skip path loses nothing. For a tool whose worst failure mode is silent data loss, that is the right thing to have made hard to regress.
  • Failure is contained at file granularity, not run granularity. FileScanner catches UnauthorizedAccessException/IOException per directory and per file and keeps walking; DuplicateFinder catches the same two types per hash task into a ConcurrentBag of warnings surfaced under `-v`. The catch filters are narrow (`when (ex is IOException or UnauthorizedAccessException)`), so real bugs still propagate — a scan of a home directory always hits unreadable files, and throwing would waste the entire scan.

BerriAI/litellm

Stale spend counters kept returning HTTP 429 after a budget window had rolled over.

A production LLM gateway with more than fifty thousand stars. Resetting an end-user budget cleared the spend in Postgres but left the cached counter alive on other workers and replicas, so requests kept being rejected against a budget that had already reset. The fix invalidates the counter across the cache tier, and ships with dedicated regression tests and a documented two-replica reproduction.

concurrent-cache-dotnet9

Lock-based LRU+TTL cache in Python with a compare-and-swap API, plus a small C# sketch

The functioning implementation is `src/cache.py`: `ConcurrentMemoryCache` backed by an `OrderedDict` under a single `threading.Lock`. `get` handles TTL expiry inline (deleting the expired entry and counting it as both a miss and an eviction) and does an LRU touch via `move_to_end`; `set` bumps a per-entry `version` on overwrite and evicts

  • `compare_and_swap` gives the cache a real read-modify-write primitive, and the test drives it properly — 5 threads x 100 retry-loop increments asserting an exact final value of 500, which is a genuine race-condition test rather than a smoke check
